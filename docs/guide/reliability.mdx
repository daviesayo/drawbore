---
title: "Reliability: isolation, halting, and resume"
description: "How Drawbore keeps a high-stakes run safe and recoverable."
---

Drawbore is built to **stop safely**, not to guess. Three guarantees:

## Each agent sees only what it was given

The framework constructs every agent's input from explicit bindings — it cannot
receive fields it was not handed. External input is bounded in size and depth
before the run starts, and is always treated as **data**, never as instructions.

## On any failure, the run halts

A schema mismatch, a blocked tool call, a runaway loop, or an agent error all
stop the run and report exactly which step failed and why. Drawbore never
continues with a partial or degraded result unless a pipeline explicitly opts in.

```python
result = await pipeline.run(Order(id="A-1"))
if result.status == "halted":
    print(result.halted_at, result.reason)   # e.g. "charge", "circuit_breaker: ..."
```

## A halted run can resume where it stopped

Give the run a stable id and a checkpoint store. Steps that already succeeded are
skipped on the next attempt — the run picks up from the first incomplete step.
The returned `RunResult` echoes the resolved `run_id`, so a defaulted run is
still inspectable after the fact.

```python
from drawbore.state import InMemoryCheckpointStore

store = InMemoryCheckpointStore()
first = await pipeline.run(order, run_id="order-A-1", checkpoints=store)   # halts at step 3
again = await pipeline.run(order, run_id="order-A-1", checkpoints=store)   # resumes at step 3
```

## Branching on a halt

`RunResult.halt_code` carries one stable token per halted run — the same closed
vocabulary the audit trail uses (`schema_violation`, `tool_access`,
`circuit_breaker`, `condition_tainted`, ...). Branch on `halt_code`, never on the
prose in `reason`; the prose is for humans and may be reworded.

An `approval_rejected` halt means a human reviewer rejected the step's proposed
output; it is terminal for that request. Re-running the pipeline mints a fresh
approval request.

A `confidence_approval_pending` halt means a `HasConfidence` step produced a
result below the pipeline's `confidence_threshold` in sync mode and a checkpoint
store was present, so the run minted a resumable approval request instead of
dying — resolve it with the same approve/amend/reject decision a
`requires_human_approval` gate uses. Without a checkpoint store the same trigger
halts terminally as `confidence_below_threshold` (a resume is impossible without
a store). A step that declares both a low confidence and `requires_human_approval`
goes through the explicit approval gate (`requires_human_approval`), never the
confidence cycle.

An `approval_error` halt means an approval decision could not be applied: no
pending request matched, the request id was stale or mismatched, the decision
was replayed (already consumed), or the run never consumed the decision.

A `resume_drift` halt means a checkpointed run was resumed after the
pipeline's topology or an agent's declared contract changed; see
[Durable resume](/guide/durable-resume) for the refusal semantics and the
resume ledger.

A `model_error` halt means the model returned output Drawbore cannot use after the
[structured-output boundary](/guide/production-llm-gateway) — including its one bounded
corrective reprompt — did not recover a usable JSON object; the reason carries a bounded
excerpt of the offending output.

An `effect_divergence` halt means that on durable resume a tool call did not match the
recorded effect sequence at its expected position, or that recorded effects were left
unconsumed at step end (the resumed run fired fewer effectful calls than were recorded,
skipping an already-fired effect). The run halts for human reconciliation rather than
risk a double-fire or silent replay gap.

An `effect_unresolved` halt means that on resume the ledger found a PENDING entry — an
effect that started but whose completion was never durably confirmed. The framework
cannot prove the call succeeded exactly once, so it halts fail-closed. The recorded
idempotency key lets an operator verify the outcome against the remote system before
clearing the entry.

An `effect_ledger_error` halt means a durable effect-ledger write failed. The result
is not returned rather than risk an unrecorded effect — a result returned without a
durable record would be invisible on the next resume, causing a silent re-fire.

## Schema fingerprints and Pydantic versions

Three safety controls key off SHA-256 fingerprints of Pydantic's
`model_json_schema()` output: the `resume_drift` step seal, the authority diff and
config drift check, and the agent re-attestation surface. All three compare a
fingerprint recorded at one point in time against one computed later.

Pydantic's JSON schema output can change shape across minor releases — enum encoding,
`$defs` ordering, `anyOf`/`null` representation, and constraint keyword placement have
all shifted historically. When `model_json_schema()` output changes, a fingerprint
computed under Pydantic X no longer equals one computed under Pydantic Y even with no
code change, producing a false-positive `resume_drift` halt, a phantom authority
regression, or a spurious forced re-attestation.

**Practical guidance:**

- If your deployment persists checkpoints, pipeline manifests, or agent identity
  records, **pin the Pydantic minor version** (e.g. `pydantic>=2.13,<2.14`) so
  fingerprints remain stable across restarts.
- After a deliberate Pydantic upgrade, expect a one-time re-attestation for any
  agent whose schema fingerprint changes. Re-export any pipeline manifests
  (`to_json`) and recompute step seals before resuming checkpointed runs.
- The CI golden tests in `tests/config/test_fingerprint_golden.py` record the
  Pydantic version they were pinned against. If those tests fail after a version
  bump, it confirms a schema-output shift rather than a Drawbore regression.
