An agent is **dumb on purpose**. When it needs to reach the outside world — read a
record, call an API — it does so through a **tool**, and only a tool it explicitly
declared. Every tool call passes through a proxy that checks a single-use
permission, enforces scope, logs the call, and stops runaway loops.

## Register a tool

```python
from drawbore.tools import ToolRegistry

registry = ToolRegistry()

async def read_transaction(args):
    return {"id": args["id"], "amount": 100.0, "currency": "USD"}

registry.register_tool("transactions_db.read_transaction", read_transaction)
```

## The default registry is process-global

A `Pipeline` built without `registry=` uses a module-level default registry.
Tools registered on it persist for the process lifetime — convenient in a
script, a contamination hazard in a test suite or long-lived service. Prefer a
fresh `ToolRegistry()` per pipeline (as every example in this guide does) and
pass it explicitly: `Pipeline(name=..., registry=registry)`.

## Declare it on an agent

The agent lists exactly the tools it may use. It receives a `tools` object that
exposes **only** those tools — nothing else.

```python
from drawbore import agent
from drawbore.tools import ToolContext

@agent(input=TxQuery, output=Tx, tools=["transactions_db.read_transaction"])
async def retrieve(query: TxQuery, tools: ToolContext) -> Tx:
    row = await tools.call("transactions_db.read_transaction", {"id": query.id})
    return Tx(**row)
```

## What the framework guarantees

- **Least privilege.** Calling a tool the agent did not declare is refused. The
  agent never holds a credential or the real handler — only a way to ask.
- **Single-use permission.** Each call mints a fresh, one-time, non-transferable
  token scoped to that tool and that run. It cannot be saved, copied, or reused.
- **A single chokepoint.** There is no path from an agent to a tool that skips
  the proxy. Every call is logged (what tool, when, hashes of input and output).
- **No runaway loops.** If an agent calls the same tool too many times in one
  run, the circuit breaker stops it — the loop dies here, not on your bill.

## Circuit-breaker caps

The proxy enforces two layers of circuit-breaker protection. Both layers use the
same halt vocabulary (`halt_code == "circuit_breaker"`, proxy-log result
`"denied:breaker"`) — distinguish them by reading the legible `result.reason`
string.

### Per-step-per-tool cap

The default `max_calls_per_tool=3` limit counts calls **per tool, per agent
step**. When an agent calls the same tool more than three times in one step, the
proxy halts immediately:

```
"tool 'payments_db.read_record' called more than 3 times by step charge in run 'order-A-1'"
```

### Run-level caps

Two additional caps bound the run's **aggregate** tool activity across every step
and every agent:

| kwarg | default | what it bounds |
|---|---|---|
| `max_tool_calls_per_run` | `500` | total admitted tool calls for the entire run |
| `max_distinct_tools_per_run` | `50` | number of distinct tool names admitted in one run |

Pass any of the three knobs to `pipeline.run(...)` to tune them tighter:

```python
result = await pipeline.run(
    order,
    max_calls_per_tool=5,
    max_tool_calls_per_run=100,
    max_distinct_tools_per_run=10,
)
```

All three are always-on and can only be set to a value of 1 or greater — they
cannot be disabled. A breach halts the run immediately:

```
"run 'order-A-1' exceeded the max-tool-calls-per-run cap (cap 100)"
"run 'order-A-1' exceeded the max-distinct-tools-per-run cap (cap 10); blocked new tool 'reports_db.read_summary'"
```

To tell a per-step breach from a run-level breach, read `result.reason`. The
per-step message names the step and the tool; the run-level message names the
run and the cap that tripped. Branch on `halt_code` for stable routing and use
the prose only for operator logging. See [Reliability](/guide/reliability) for
the full halt-code vocabulary.

## Register a pipeline against a registry

```python
from drawbore import Pipeline

pipeline = Pipeline(name="confirm", registry=registry)
pipeline.add(retrieve)   # rejected at this line if 'retrieve' declares a tool
                         # that isn't registered
```

## Instrumenting and observing tool calls

You do not need to wrap a tool handler to observe it. Every tool call — custom,
MCP, and builtin — passes through the proxy before it reaches the handler. The
proxy records timing, input/output hashes, and disposition for every call, and
emits an `execute_tool` OTel span. That includes tools registered by
`register_mcp_server` or by the framework itself, not only handlers you wrote.

**Read timing and disposition from `result.metrics.tool_calls`:**

```python
result = await pipeline.run(input)

for call in result.metrics.tool_calls:
    print(call.tool, call.operation, call.duration_seconds, call.result)
    # 'mcp://identity/verify' invoke 0.08 ok
```

Each `ToolCallMetric` carries `.tool`, `.operation`, `.duration_seconds`, and
`.result` (one of `"ok"`, `"error"`, or a `"denied:*"` label). For spans and
the full observability picture — including how to export to Axiom, Datadog, or
any OTLP backend — see [Observability and audit](/guide/observability-audit).

**Inject a fault in a test:** supply a callable as the mock, and raise from it:

```python
async def _fail(_args):
    raise RuntimeError("database unavailable")

async with pipeline.test_mode(
    mock_tools={"transactions_db.read_transaction": _fail},
) as test:
    result = await test.run(...)
```

The callable mock still flows through the real proxy, JIT token, and circuit
breaker. For more on test mode see [Local test mode](/guide/local-testing).

**Transform a tool you author:** wrap your handler before registration:

```python
async def read_transaction(args):
    return {"id": args["id"], "amount": 100.0, "currency": "USD"}

async def audited_read(args):
    result = await read_transaction(args)
    # any additional side effects you own
    return result

registry.register_tool("transactions_db.read_transaction", audited_read)
```

**What is not provided:** drawbore does not offer a post-registration hook that
intercepts or mutates a tool's inputs or substitutes its outputs — for any kind
of tool (custom, MCP, or builtin). The proxy is the single enforcement
chokepoint, and the audit `input_hash` is computed before the handler runs, so
an interceptor that altered inputs or outputs would break audit-record integrity
and bypass enforcement. If you need per-call transformation for a tool you
author, wrap the handler before registration as shown above.

## Exactly-once resume for effectful tools

Tools default to `effectful=True`. On a crash+resume, effectful calls recorded
in the effect ledger are replayed from the ledger instead of being re-fired.
Mark pure read-only tools `effectful=False` so resume re-queries them live
rather than replaying a stale result. See [Durable resume](/guide/durable-resume#exactly-once-effects) for
the full semantics, the `current_idempotency_key()` accessor, and the
`EffectLedger` interface.
