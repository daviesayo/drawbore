title: "Observability and audit: see what every run did"

Drawbore is the telemetry source; you own the drain. Every run emits OpenTelemetry
spans following the GenAI Semantic Conventions, and produces a separate,
append-only audit record. Both are in the MIT core and always on.

## Spans: the operational view

Three span types, at the points that matter:

- `execute_tool {tool}` — every tool call, at the proxy (the one chokepoint).
- `invoke_agent {agent}` — every step, tagged with the agent name, version, risk
  tier, and run id.
- `chat {model}` — every model call, with the requested and actual model.

Each span carries the run id, step, and input/output hashes, so you can answer
"what happened in run X" by querying the `drawbore.run_id` attribute. You don't
configure anything to get spans — they emit to whatever OpenTelemetry provider is
configured in your process.

## Send spans to your drain

To export to Axiom, Datadog, Grafana, Honeycomb, or any OTLP backend, install the
optional extra and point Drawbore at your endpoint:

```python
from drawbore.observability import configure_otlp_export

configure_otlp_export("https://otlp.your-drain.example", headers={"authorization": "..."})
# requires `pip install drawbore[otlp]`
```

Without the extra, this fails closed with a clear error telling you to install it —
the framework never silently drops your telemetry config.

## Audit: the compliance view

Separate from spans, every run produces an immutable audit record — a trace a
compliance officer can read without an engineer:

```python
from drawbore.audit import InMemoryAuditSink

my_sink = InMemoryAuditSink()
result = await pipeline.run(transaction, audit=my_sink, tenant_id="acme")

print(result.audit_trace.legible())
# Run 'run-1' of pipeline 'remittance' v1.0.0 (tenant acme): completed.
# Steps completed: 4.
# Escalations: 0.
# Schema violations: 0.
# - step 0 'validate' v1.0.0: ok
# ...
```

`result.audit_trace` is always set on a returned run (`.steps`, `.escalations`,
`.schema_violations`, and per-step detail). Supply an `AuditSink` to persist
records; the in-process `InMemoryAuditSink` (from `drawbore.audit`) is the default
for tests and local runs.

When a run can't proceed — a [halt or escalation](/guide/escalation) — the same
record names the step it stopped at and why, so the trace reads end-to-end whether
the run completed or not.

## Metrics: the cost and performance view

The audit record answers "what happened"; `result.metrics` answers "how much did
it cost and how long did it take". It is a separate, quantitative object present on
every run, so you can run a cost or performance analysis off the public surface
without re-deriving anything out of band:

```python
result = await pipeline.run(transaction)

for step in result.metrics.steps:
    print(step.agent, step.duration_seconds, step.tokens, step.cost)
    # 'risk_scorer' 0.42 TokenUsage(input_tokens=812, output_tokens=64, total_tokens=876) 0.0013

for call in result.metrics.tool_calls:
    print(call.tool, call.operation, call.duration_seconds, call.result)
    # 'mcp://identity/verify' invoke 0.08 ok

blob = result.metrics.to_dict()   # JSON-safe primitives for export
```

Each step carries its wall-clock `duration_seconds`, and — for a model-backed step —
the call's `tokens` (a provider-agnostic `TokenUsage` of `input_tokens` /
`output_tokens` / `total_tokens`) and provider-reported `cost`. Both `tokens` and
`cost` are `None` when the provider does not report them; Drawbore never fabricates a
cost from a pricing table. `tool_calls` is the proxy's per-call log (tool, operation,
duration, disposition) — the same chokepoint the spans and audit trail see, so
metrics correlate to the audit trace by `run_id` and step index.

Spans can be sampled and dropped by your drain; the audit record is not — it is the
defensible answer to "show me exactly what happened to transaction X." The
open-source core gives you the basic, readable, exportable log; tamper-evident,
cryptographically signed, compliance-formatted export is part of the managed
service.
