---
title: "Durable resume"
description: "Resume a checkpointed run safely — and refuse the resume when the pipeline changed underneath it."
---

Use durable resume when a pipeline run can halt partway (a model outage, an
escalation, a crash) and you want to continue it later without re-executing
the steps that already succeeded. Drawbore's resume is refuse-on-drift: before
restoring anything, the runtime verifies that the pipeline still means what it
meant when the checkpoint was taken. If an agent's declared contract or the
pipeline's topology changed, the resume halts with `halt_code ==
"resume_drift"` instead of replaying outputs into changed logic — and it halts
before executing a single step.

## Resuming a run

Pass a checkpoint store and a stable `run_id`:

```python
from drawbore.state import InMemoryCheckpointStore

store = InMemoryCheckpointStore()
first = await pipeline.run(order, run_id="order-A-1", checkpoints=store)   # halts at step 3
again = await pipeline.run(order, run_id="order-A-1", checkpoints=store)  # resumes at step 3
```

Completed steps are restored from the store, not re-executed. Each completed
step also records a **seal** — a snapshot of the agent's declared contract
(version, risk tier, tools, model, fallback model, instructions, input/output
schemas, approval requirement, and the step's evidence policy).

## Resuming across a process restart

`InMemoryCheckpointStore` lives only for the lifetime of the process, so it
resumes within one run of your program. To resume after the process exits — a
worker that crashes and restarts, a job picked up by a different machine — use
`FileCheckpointStore`, which persists the full checkpoint (outputs, skip marks,
topology fingerprint, seals, and trust labels) to a directory:

```python
from drawbore.state import FileCheckpointStore

# First process: runs until it halts, persisting each completed step.
store = FileCheckpointStore("/var/lib/myapp/checkpoints")
first = await pipeline.run(order, run_id="order-A-1", checkpoints=store)

# A later process (a restart): a brand-new store over the same directory
# restores the completed steps and resumes — no re-execution, no spurious drift.
store = FileCheckpointStore("/var/lib/myapp/checkpoints")
again = await pipeline.run(order, run_id="order-A-1", checkpoints=store)
```

Each step is written atomically (write a temp file, then rename), so a crash
mid-write never leaves a torn checkpoint: the previous committed step stays
intact and a half-written file is ignored on the next read.

Outputs are stored as plain field data, not a Python class path. On resume the
store rebuilds each typed output from the *live* pipeline's output schema for
that step, so a tampered checkpoint file can never make the store import an
arbitrary type. (This is why the same pipeline, with matching declarations,
must be rebuilt before you resume — exactly what the seal also verifies.)

## When resume says no

On resume, every stored seal is re-verified against the live pipeline before
anything runs. A mismatch refuses the whole resume:

```python
# Between attempts, someone changed the writer's model...
result = await pipeline.run(order, run_id="order-A-1", checkpoints=store)
assert result.status == "halted"
assert result.halt_code == "resume_drift"
print(result.reason)
# resume_drift: step 'confirmation_writer' changed since checkpoint (model); refusing to resume
```

Refusal is pre-flight: zero steps execute, so a refused resume has zero side
effects and never double-fires a completed step. Topology changes (steps
added, removed, or rewired) refuse the same way when the run had prior
progress; a `run_id` that never completed any step simply starts fresh.

## The resume ledger

Every run result carries `resume_ledger` — a regulator-readable record of what
the runtime observed:

```python
print(result.resume_ledger.legible())
# Run 'order-A-1': resumed from checkpointed state.
# Step 2 'confirmation_writer': resume refused — changed since checkpoint (model).
# 2 completed step(s) verified clean; resume was refused before any restore.
```

Each entry names the step, its disposition (`executed`, `restored`, `skipped`,
or `refused`), and the seal verdict. Branch on `halt_code`, never on the prose
(see [Reliability](/guide/reliability)).

## What the seal does and does not cover

The seal covers **declared** semantics. It does not fingerprint Python
function bodies: changing an agent's implementation without bumping `version`
is invisible to the seal. Bump `version` on any behavior change — that is the
author's half of the contract.

Two more boundaries to know:

- **Concurrent resumes are not serialized.** Two workers resuming the same
  `run_id` at the same time both pass verification and both execute. The seal
  refuses drifted resumes; it does not make execution single-use.
- **Custom checkpoint stores must persist seals.** `FileCheckpointStore`
  already does; if you write your own store, a store that implements only the
  older interface restores outputs but returns no seals, and an unverifiable
  step refuses the resume with `resume_drift` until the store implements
  `record_seal`/`seal_of`. Implement both together, and persist a step's
  output, trust, and seal atomically. Checkpoints written before seals existed
  also refuse with `resume_drift`: re-run those flows fresh under a new
  `run_id`.

## Exactly-once effects

Checkpointing resumes at the first incomplete step. But what about a step that
had already fired some effectful tool calls — a charge, a notification, an
external write — before the crash? Without extra bookkeeping, those calls would
fire again.

The **effect ledger** solves this. When a step resumes, each effectful tool call
is replayed from the ledger instead of being re-fired: the recorded output is
returned, and the real handler is never called a second time.

### Mark tools as effectful or read-only

Every tool defaults to `effectful=True` — the fail-closed choice. An
unclassified tool is treated as effectful so it is never silently double-fired.
Mark pure read-only tools `effectful=False` so resume re-queries them live
instead of replaying a stale recorded result:

```python
registry.register_tool(
    "payments.charge",
    charge_handler,
    effectful=True,    # default; explicit for clarity
)
registry.register_tool(
    "records.read_customer",
    read_customer,
    effectful=False,   # safe to re-query; no ledger overhead
)
```

`effectful` is supported on `register_tool`, `register_builtin`, and
`register_mcp_tool`. The builtin `evidence://retrieve` is already registered
`effectful=False`.

### Wire the ledger alongside the checkpoint store

Pass an `effect_ledger` together with `checkpoints` and a fixed `run_id`:

```python
from drawbore.state import FileCheckpointStore, InMemoryEffectLedger

store = FileCheckpointStore("/var/lib/myapp/checkpoints")
ledger = InMemoryEffectLedger()

first = await pipeline.run(order, run_id="order-A-1", checkpoints=store, effect_ledger=ledger)
# process crashes partway...
again = await pipeline.run(order, run_id="order-A-1", checkpoints=store, effect_ledger=ledger)
# effectful calls already recorded are replayed, never re-fired
```

The same `effect_ledger=` kwarg works with `pipeline.test_mode(...).run(...)`.

### What happens on resume

For each effectful call in the resuming step the proxy looks up the position in
the ledger:

- **No entry found** — first-time execution; the handler is called normally and
  the result is recorded.
- **Entry found, `SUCCEEDED`** — the recorded output is returned; the handler
  is not called.
- **Entry found, `PENDING`** — the handler fired but the ledger's confirmation
  write was lost in the crash. The framework cannot prove the call succeeded
  exactly once, so it halts `effect_unresolved` fail-closed. The recorded
  idempotency key lets an operator verify the outcome against the remote system.
  Resolving a pending entry (clearing or voiding it) is not yet part of the
  public API; the run halts for human reconciliation.
- **Divergence** — a call at a recorded position does not match what was
  recorded (different tool or different arguments), or the resuming step fires
  fewer effectful calls than were recorded (skipping a previously-fired effect).
  The run halts `effect_divergence` rather than risk a double-fire or silent
  replay gap.

See [Reliability](/guide/reliability) for the full halt-code vocabulary.

### Deterministic steps vs. model-driven loops

The replay contract is strongest for **deterministic steps**: the same inputs
always produce the same tool-call sequence, so a resumed deterministic step
replays cleanly. Model-driven agentic loops are non-deterministic in call order:
a resumed loop either reproduces the recorded sequence exactly or halts
`effect_divergence` fail-closed. Design effectful agentic loops with that
trade-off in mind.

### Remote dedup with `current_idempotency_key()`

There is a one-window residual risk: the handler succeeds, but the process
crashes before the ledger records `SUCCEEDED`. On the next resume the ledger
finds `PENDING` and halts. For calls to remote systems that support idempotency
keys (Stripe, Adyen, most payment processors), you can push the dedup downstream
and close the window:

```python
from drawbore.tools import current_idempotency_key

async def charge_handler(args):
    key = current_idempotency_key()  # stable hex key, unique per run/step/position/tool
    return await stripe.charge(
        amount=args["amount"],
        idempotency_key=key,         # remote system deduplicates on its side
    )
```

`current_idempotency_key()` returns the key while inside an effectful tool call
and `None` outside one.

### Ledger types

All four types are exported from `drawbore.state`:

| Type | Role |
|------|------|
| `EffectLedger` | ABC — implement this for a durable backend |
| `InMemoryEffectLedger` | Default in-process implementation |
| `EffectEntry` | A single recorded call (`run_id`, `step`, `position`, `tool_ref`, `input_hash`, `idempotency_key`, `status`, `output`) |
| `EffectStatus` | `"pending"` or `"succeeded"` |

### Durable ledger backends

`InMemoryEffectLedger` does not survive process restart. For real
crash-and-resume across machine failures, implement `EffectLedger` with a
durable backend — a database row, a file, a cloud store. The interface mirrors
`CheckpointStore`: a small, synchronous ABC with `record_pending`,
`record_succeeded`, `entry_at`, `recorded_count`, and `entries_from`. All writes
must be durable before the method returns; async I/O must be bridged internally.

### Use `unclassified_effectful_tools()` as a CI check

```python
from drawbore.tools import unclassified_effectful_tools

unclassified = unclassified_effectful_tools(registry)
assert not unclassified, f"tools still at default effectful=True: {unclassified}"
```

This returns all tools currently marked effectful (the default), as candidates
to review and mark `effectful=False` if they are pure reads.

## Common mistakes

- **Reusing a `run_id` for a different request.** Resume is keyed by `run_id`;
  a reused id restores the previous run's outputs. Use one id per logical run.
- **Upgrading Pydantic mid-run.** Schema fingerprints can change across
  Pydantic minor versions, which reads as drift and refuses the resume. Safe,
  but plan upgrades between runs, not across them.
- **Treating `resume_drift` as retryable.** It is not transient. Either
  restore the pipeline to the checkpointed semantics, or start a fresh
  `run_id` under the new ones.
- **Passing a ledger without a checkpoint store.** The ledger and checkpoint
  store are complementary: the store skips already-completed steps; the ledger
  replays already-fired effects within a step. Neither alone prevents both
  classes of double-execution.
- **Using `InMemoryEffectLedger` across process restarts.** It does not
  persist. Use a durable backend if your resume must survive a process exit.
